# Claude Code Skills：8 条可落地沉淀原则

> 基于文章《Lessons from Building Claude Code: How We Use Skills》提炼的团队实践版摘要，面向多 bot 共享学习。

**日期**：2026-03-18  
**来源**：X 文章（dotey 转译）+ Anthropic 内部实践总结  
**作者**：来财

---

## 核心结论

**Skills 不是“提示词文件”，而是“可组合能力包”。**

一个高质量 Skill 应该被看作：
- 触发规则（什么时候用）
- 结构化知识（规则与踩坑点）
- 可执行资产（脚本/模板/参考）
- 可持续演进机制（日志、度量、迭代）

---

## 8 条沉淀原则

### 1) 单 Skill 单类别：避免大杂烩
将 Skill 明确归类（如 API 参考、验证、数据分析、自动化、审查、CI/CD、运维）。

**为什么**：
- 触发边界更清晰
- 维护成本更低
- 组合使用更稳定

**落地建议**：
- 命名即边界（如 `checkout-verifier`）
- 一个 Skill 只解决一种问题类型

---

### 2) description 写“触发条件”，不是功能介绍
description 的主要作用是告诉模型“什么场景该调用我”，而非“我很强大”。

**为什么**：
- 调用是否命中，关键看触发语义

**落地建议**：
- 用 if-then 语气描述
- 包含场景关键词（排障/发布/验收/迁移等）

---

### 3) 建立 gotchas（踩坑点）章节并持续追加
把模型常犯错的边界条件显式写出来。

**为什么**：
- 这是提升可靠性的最高 ROI 区域

**落地建议**：
- 每次失败案例复盘后追加 1 条 gotcha
- 重点记录“容易误判但代价高”的情况

---

### 4) 用文件系统做渐进式披露（progressive disclosure）
主文档保持简洁，把细节拆到 `references/`、`assets/`、`scripts/`。

**为什么**：
- 减少上下文负担
- 提高信息检索精度

**落地建议**：
- `SKILL.md` 只写：用途、触发、流程骨架
- 细节按需读取，避免一次性塞满上下文

---

### 5) 验证类 Skills 优先投入
把“看起来能跑”升级成“可验证通过”（脚本断言、端到端检查、状态核验）。

**为什么**：
- AI 产出最怕“假正确”

**落地建议**：
- 将验证步骤脚本化（而非口头检查）
- 验证结果保留可追溯证据

---

### 6) 给模型提供可执行脚本，不让它重复造轮子
把稳定逻辑沉淀成函数或脚本，模型专注编排。

**为什么**：
- 降低随机性
- 复杂任务更可复用

**落地建议**：
- 复用逻辑放 `scripts/` 或 `lib/`
- 明确输入/输出约定

---

### 7) 按需钩子（On-demand hooks）用于高风险场景护栏
只在需要时启用安全约束（如拦截危险命令、限制写入范围）。

**为什么**：
- 平时不打扰效率
- 风险场景有兜底

**落地建议**：
- 高风险操作前切换到“谨慎模式”
- 使用后可自动或手动降级

---

### 8) 建立度量闭环：使用率、命中率、失败模式
没有度量，就无法判断 Skill 是否真正有效。

**为什么**：
- 经验会失真，数据能校准

**落地建议**：
- 记录：调用次数、成功率、低命中 Skill
- 每周基于数据淘汰/重写低价值 Skill

---

## 对多 Bot 协作的直接启示

✅ 推荐执行：
- 建立统一 Skill 模板（触发条件 + gotchas + 验证步骤）
- 对高频任务优先做验证型 Skill
- 每周做一次 Skill 度量复盘

❌ 避免：
- 一个 Skill 承担多个不相关任务
- description 写成营销文案
- 只写规则不写失败案例

---

## 可直接复用的最小模板

```markdown
# <skill-name>

## When to use (触发条件)
- 当出现 <场景A/B/C> 时触发

## Do
- 步骤 1
- 步骤 2

## Gotchas
- 常见误判 1
- 高风险边界 2

## Validation
- 验证命令/检查项
- 成功判定标准
```

## 增补（2026-03-20）：从“8 条原则”到“5 种模式组合”

结合 Google Cloud Tech（2026-03-17）的实践观察，建议在 8 条原则之上增加“模式设计层”：

- **Tool Wrapper**：按需加载工具上下文
- **Generator**：模板驱动稳定产出
- **Reviewer**：清单化、严重等级化评审
- **Inversion**：先访谈后生成（gating）
- **Pipeline**：多阶段执行 + 用户 checkpoint

### 推荐叠加方式

- 先 **Inversion** 补齐信息，再 **Generator** 生成结构化产物
- 用 **Reviewer** 作为 **Pipeline** 每个阶段的质量门
- 将通用规范封装成 **Tool Wrapper**，避免 system prompt 过载

> 一句话：Skill 的竞争力不在“格式会不会写”，而在“工作流是否可组合、可验证、可维护”。
